# RF01 Registrar cuenta

Backend implementado con el contrato REST confirmado en esta conversación.
La versión legal de privacidad sigue pendiente: sin una versión vigente externa,
el registro responde 503 y no crea datos. `FIXTURE-NO-LEGAL` aparece exclusivamente
en pruebas y no constituye una política aprobada.

## Alcance y fuentes

- Documentos funcionales 00–06 de Elsa y CC-RF01-01: se elimina únicamente la
  validación semántica/catálogo de palabras del nombre.
- Migraciones existentes V1–V4; ninguna modificada ni añadida.
- No se implementan RF02, RF06, OTP, pantallas Android ni sesiones automáticas.
- A01/A02 de RF01 son interacciones Android sin operación backend. A03 impide el
  envío local; el backend revalida toda solicitud. A04 rechaza el correo ocupado
  por PENDIENTE_ELIMINACION sin revelar ese estado.

## Contrato confirmado

`POST /api/v1/auth/registro`, público, JSON:

```json
{
  "nombre": "Ana María",
  "apellido": "D'Ávila",
  "correo": "ana@example.com",
  "fechaNacimiento": "1995-01-01",
  "contrasena": "<contraseña elegida>",
  "confirmacionContrasena": "<misma contraseña>",
  "consentimientoPrivacidad": {
    "aceptado": true,
    "version": "<versión legal aprobada y configurada externamente>"
  }
}
```

Éxito HTTP 201:

```json
{"resultado":"CUENTA_CREADA","destino":"INICIO_SESION"}
```

Errores con forma `{codigo,mensaje,erroresPorCampo}`; nunca incluyen valores
rechazados, contraseñas, hashes, tokens ni detalles SQL:

| HTTP | Código | Condición |
|---|---|---|
| 400 | VALIDACION | Campos, fecha JSON, consentimiento o versión aceptada inválidos |
| 409 | CORREO_NO_DISPONIBLE | Correo ocupado; mensaje uniforme «Correo no disponible.» |
| 503 | REGISTRO_NO_DISPONIBLE | Versión vigente ausente, FREE no habilitado o fallo de persistencia |
| 500 | ERROR_INTERNO | Error inesperado, sin detalles internos |

## Configuración y seguridad

Configurar externamente `mycar.registro.privacidad.version-vigente` con la versión
real que apruebe el equipo. No hay valor legal predeterminado. Se exige coincidencia
exacta con la versión aceptada. La fecha de aceptación se obtiene del reloj del servidor;
no se acepta del cliente. Esta corrección no inventa el contenido del aviso legal.

La cadena de seguridad pública coincide solo con la ruta de registro. Es stateless,
sin autenticación por cookie ni CSRF para ese POST JSON público. No crea JSESSIONID.
Una cadena de respaldo conserva health público y deniega otras rutas; los futuros
RF deben aportar su política de autenticación/autorización. No hay login/logout
funcionales implementados por esta entrega.

Hash Argon2id v19: sal aleatoria de 16 bytes, salida de 32 bytes, memoria de 19 MiB,
2 iteraciones y paralelismo 1, mediante Spring Security y Bouncy Castle 1.86. Es la
configuración mínima de [OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
Antes de desplegar, medir el coste en el servidor de destino y ajustar si corresponde.
[Spring Security](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)
documenta la dependencia Bouncy Castle; la [versión 1.86](https://www.bouncycastle.org/resources/new-release-bouncy-castle-java-1-86/)
es una publicación oficial. No se truncan ni transforman las contraseñas.

Los nombres normalizan secuencias de espacios Unicode a un espacio y recortan extremos;
se admiten letras Unicode y marcas combinantes, espacios, guion y apóstrofos recto/tipográfico
entre letras. La longitud se cuenta por puntos de código, como PostgreSQL. El correo
solo recorta extremos y convierte a minúsculas con Locale.ROOT; conserva puntos y alias.
La edad usa años cumplidos y America/Lima, coherente con el trigger existente.

## Organización de responsabilidades

- `registro/web`: DTO sin representación de secretos, controlador, errores y seguridad.
- `RegistrationValidator`: validaciones y normalización, sin catálogo semántico.
- `RegistrationPrivacyPolicy`: comprobación de la versión externa aceptada.
- `RegisterAccount`: caso de uso transaccional; depende del puerto RegistrationStore
  y de PasswordEncoder. Devuelve un ID interno que no se expone en HTTP.
- `persistence/JdbcRegistrationStore`: consultas parametrizadas sobre los nombres
  físicos reales, utilizando la misma transacción y datasource de Spring.
- `RegistrationConfiguration`: reloj y Argon2id.

Se emplea JDBC con las dependencias ya disponibles; no se duplicó el esquema con
un conjunto adicional de entidades JPA. `@Transactional` coordina las cuatro filas:
usuario ACTIVA/USUARIO, suscripción FREE ACTIVA sin fin, configuración global KM
PAUSADO y preferencias ON/ON/ON/NO_SOLICITADO. FREE se busca por código y activo,
sin ID fijo. El índice único resuelve también carreras que superan la consulta previa.

## Pruebas y evidencias

Resultado verificado el 27/10/2026: **45 pruebas, 0 fallos, 0 errores, 0 omitidas**.
Java 21; PostgreSQL 17 desechable; integración HTTP mediante MockMvc con filtros
reales de Spring Security, sin servidor HTTP de producción ni base del equipo.

| Clase | Casos | Cobertura |
|---|---:|---|
| RegistrationValidatorTest | 25 | Formatos, normalización, edad Lima y límites, contraseña y consentimiento |
| RegisterAccountTest | 4 | Argon2id, sal, ausencia de truncamiento, coordinación, duplicados y versión ausente |
| RegistrationWebTest | 3 | Respuestas 500/503 sanitizadas y DTO sin secretos en toString |
| RegistrationIntegrationTest | 12 | 201 público, cuatro filas, FREE con ID distinto, tres estados duplicados, carrera, tres rollbacks y errores HTTP |
| RegistrationPrivacyUnavailableIntegrationTest | 1 | 503 y ausencia de escrituras cuando falta configuración legal |

Desde la raíz, con Docker Desktop disponible y JAVA_HOME apuntando a JDK 21:

```powershell
py -3 scripts/test_rf01.py
```

Linux/macOS: `python3 scripts/test_rf01.py`.

El ejecutor crea un contenedor etiquetado exclusivo con credenciales aleatorias,
base `mycar_rf01_test_*` y puerto temporal de loopback. Spring aplica únicamente
V1–V4 allí. Las pruebas inyectan fallos con restricciones temporales exclusivamente
en esa base desechable; no constituyen migraciones nuevas. Al terminar, se comprueba
la identidad del contenedor antes de eliminarlo y sus volúmenes anónimos.
No se lee `.env`, no se monta el volumen compartido y no se usa Compose.

Solo pruebas unitarias, desde `backend/`:

```powershell
.\mvnw.cmd '-Dtest=RegistrationValidatorTest,RegisterAccountTest,RegistrationWebTest' test
```

Evidencias generadas en `backend/target/` (ignoradas por Git):

- `rf01-evidencia.json`: resumen sanitizado por clase, incluido total y versión ficticia.
- `surefire-reports/TEST-backend.registro.*.xml`: resultados individuales.
- `rf01-test-run.log`: diagnóstico local del ejecutor; no usar como evidencia pública
  sin revisar, porque la autoconfiguración de Spring puede escribir una contraseña
  de desarrollo generada, ajena a las contraseñas registradas.

El primer ensayo detectó una fixture que intentaba actualizar una identidad GENERATED
ALWAYS. Se corrigió recreando FREE con la secuencia existente en la base desechable;
el ensayo final pasó completo. No se cambió el DDL para hacer pasar la prueba.

## Pendiente para habilitación real

El equipo debe aprobar el aviso legal y su versión y configurar la propiedad externa.
Mientras falte, RF01 permanece deliberadamente no disponible en el entorno real.
La suite completa sí se verifica con una versión identificada solo como fixture.
Las evidencias no certifican Android, despliegue de producción ni los RF02/RF06.
