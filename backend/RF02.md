# RF02 Iniciar sesión — implementación parcial verificable

Estado al 27/10/2026: implementados y probados login de cuentas ACTIVA, intentos
fallidos, sesiones por instalación, renovación y validación. **RF02 no está completo**:
la rama de login de cuentas no ACTIVA y la preparación de Inicio permanecen pendientes
por instrucción expresa del usuario. Los contratos HTTP se mantienen provisionales.

## Fuentes y decisiones de esta entrega

Se utilizan los documentos funcionales 00–06 de Elsa, RF002-E1, RF002-A01/A02/A03/A04,
COBERTURA_RF02_ERRORES, RN02-01 a RN02-09, V1–V4 y el código RF01 existente.
No se modificó ningún documento funcional, migración ni archivo de RF01.

Decisiones expresamente autorizadas:

- JWT HS256 con clave externa de al menos 32 bytes; acceso y sesión con duraciones externas obligatorias.
- Refresh opaco de 32 bytes aleatorios, almacenado exclusivamente como SHA-256 hexadecimal.
- Rotación atómica del refresh y vencimiento absoluto de sesión, sin extenderlo al renovar.
- Comprobar en base de datos la sesión y el estado de cuenta en cada petición protegida.
- Usar provisionalmente las rutas/DTO/respuestas propuestos, sin declararlos congelados.
- Mantener detenida la rama de login no ACTIVA; no inventar un 503 funcional para ella.
- Dejar Inicio como dependencia pendiente del módulo de consulta de vehículos.

## Límite pendiente: cuentas no ACTIVA

El BCE verifica contraseña antes de decidir acceso por estado. V4, en
`registrar_fallo_login`, retorna sin registrar eventos cuando la cuenta no es ACTIVA.
El usuario no ratificó una excepción que limitara silenciosamente el contador a ACTIVA.
No se modifican V4 ni las reglas congeladas para resolver el conflicto.

El código aísla esta rama con `NonActiveAccountDecisionPending`: no verifica contraseña,
no cuenta fallos ni crea sesiones. Es una barrera técnica deliberada, no una implementación
de la secuencia funcional. Si se invoca por HTTP, la protección genérica de errores
inesperados devuelve 500 sin detalles. **Ese 500 no es el contrato funcional definitivo
para SUSPENDIDA/PENDIENTE_ELIMINACION; no se implementó 503 ni 403 como política de esa rama.**
El equipo debe resolver orden de comprobaciones, alcance del conteo y respuesta definitiva.

La validación de sesiones ya existentes sí exige cuenta ACTIVA; una cuenta SUSPENDIDA
no puede usar una sesión previa. Esto es distinto del bloqueo temporal de nuevos logins:
el bloqueo por tres fallos no suspende la cuenta ni invalida sesiones/renovaciones vigentes.

## Contratos implementados provisionalmente

### POST /api/v1/auth/login

Público, JSON `{correo,contrasena,idInstalacion}`. `idInstalacion` es un UUID y nunca
autoriza por sí solo. El correo se recorta y pasa a minúsculas, sin reglas Gmail.
La contraseña conserva su valor exacto: login valida presencia, no reaplica complejidad RF01.

200: `{estado:"AUTENTICADO",idSesion,accessToken,accessTokenExpiraUtc,refreshToken,sesionExpiraUtc}`.
No crea cookie/JSESSIONID. Credenciales solamente en respuestas exitosas, con Cache-Control
no-store y Pragma no-cache; no en errores ni logs de aplicación.

Correo inexistente, contraseña incorrecta y restricción temporal producen el mismo
401 `CREDENCIALES_INVALIDAS` y mensaje genérico. Una cuenta inexistente no crea eventos
de fallo por cuenta. Las cuentas no ACTIVA tienen la limitación técnica descrita arriba.

### POST /api/v1/auth/renovar

Público con prueba secreta en JSON `{idInstalacion,refreshToken}`. Devuelve la misma
estructura 200. El refresh actual se consume una sola vez: el anterior deja de autorizar
renovaciones. La sesión conserva su ID y su fecha límite absoluta; no crea otra fila.
Los access tokens anteriores de esa misma sesión pueden seguir válidos hasta su propio
vencimiento; la rotación del refresh no afirma revocarlos.

La renovación no consulta ni modifica contadores de login. Puede continuar durante
un bloqueo temporal de nuevos inicios si cuenta y sesión siguen habilitadas.

### GET /api/v1/auth/sesion

Requiere `Authorization: Bearer <accessToken>`. 200:
`{vigente:true,idSesion,sesionExpiraUtc}`. Se comprueban firma HS256, emisor, audiencia,
expiración sin tolerancia de reloj adicional, identidad, instalación y sesión persistida.
La sesión debe estar VIGENTE, sin revocada_utc, no vencida y pertenecer a cuenta ACTIVA.
Un JWT válido criptográficamente no basta para autorizar una sesión reemplazada.

No se acepta idUsuario arbitrario del cliente. No se implementan GET /api/v1/inicio
ni POST /api/v1/auth/logout. Permanecen denegados por la cadena de respaldo existente.

## Configuración externa obligatoria

| Propiedad | Significado |
|---|---|
| mycar.auth.jwt-secret-base64 | Clave aleatoria, codificada Base64 estándar; al menos 32 bytes decodificados |
| mycar.auth.access-ttl | Duración ISO-8601 del acceso |
| mycar.auth.session-ttl | Duración ISO-8601 absoluta de la sesión/autoridad de renovación |

No se incorpora una clave fija ni una duración de producción predeterminada. Las duraciones
deben ser positivas, de segundos completos y acceso <= sesión. Configuración ausente no
impide iniciar RF01; las operaciones RF02 fallan cerradas. La clave debe conservarse externamente
y compartirse entre las instancias que validen esas sesiones, no generarse de nuevo en cada arranque.

Las pruebas usan PT5M/P1D únicamente como fixtures técnicas y una clave aleatoria nueva por
ejecución. No representan duraciones funcionales definitivas ni secretos de producción.

## Persistencia y transacciones

- Reutiliza `registrationPasswordEncoder` (Argon2id), sin cambiar RF01 ni reimplementar hashing.
- Bloquea usuario con FOR NO KEY UPDATE antes de verificar contraseña y decidir el login ACTIVA.
- Durante restricción vigente no verifica contraseña, inserta fallos ni extiende la fecha.
- Una contraseña incorrecta llama `registrar_fallo_login`; TransactionTemplate confirma ese
  resultado en una transacción independiente antes de lanzar el rechazo público.
- La función existente implementa ventana móvil 10 minutos, tercer fallo y bloqueo 10 minutos.
- El login correcto llama `reiniciar_fallos_login` sin borrar historial. Reinicio, sustitución
  de sesión, inserción y emisión de credenciales son atómicos; un fallo técnico revierte todo.
- Reemplaza solo sesiones VIGENTE del mismo usuario/instalación: REVOCADA con fecha, o EXPIRADA
  si ya vencieron. No modifica otras instalaciones. Respeta el índice único parcial existente.
- Refresh usa orden de bloqueo usuario -> sesión, relee el hash actual y rota dentro de la
  transacción; solicitudes concurrentes con el mismo refresh no pueden consumirlo dos veces.
- Usa `clock_timestamp()` de PostgreSQL para decisiones persistidas de bloqueo/sesión.
- No se guarda el JWT de acceso ni el refresh original, ni se añade columna/tabla alguna.

## Arquitectura y compatibilidad

`LoginValidator` valida entradas; `SessionAuthentication` coordina autenticación y transacciones;
`SessionCredentials` firma/verifica JWT y genera/deriva refresh; `AuthenticationStore` es el puerto
de persistencia y su adaptador JDBC respeta el esquema existente. API y errores están en `web`.

Se añade solo `spring-security-oauth2-jose`, con versión gestionada por Spring Boot 3.5.16
(Spring Security 6.5.11). Se usan las APIs oficiales de
[Spring Security JWT](https://docs.spring.io/spring-security/reference/6.5/servlet/oauth2/resource-server/jwt.html).
No se implementa un algoritmo criptográfico propio.

Las cadenas RF02 tienen orden 2 (login/renovación) y 3 (sesión protegida). RF01 mantiene
su cadena orden 1 y el respaldo orden 100 sin cambios. El filtro bearer se construye solo
en la cadena protegida; no es un filtro global que intercepte registro o health.
Las demás rutas siguen denegadas. No se duplicó la configuración Argon2 ni se añadió RF06.
