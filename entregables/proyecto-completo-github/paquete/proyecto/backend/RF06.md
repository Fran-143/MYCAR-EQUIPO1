## Contrato autorizado para esta implementación

`POST /api/v1/auth/logout`, sin body, con `Authorization: Bearer <accessToken>` de RF02.

- El servidor deriva usuario, sesión e instalación del JWT firmado. Ningún id libre del body
  o query selecciona la sesión objetivo.
- Se reutiliza RF02 para validar HS256, emisor, audiencia y vencimiento. Después se comprueban
  propietario, instalación, cuenta ACTIVA y vencimiento persistido, bajo bloqueo.
- Un refresh token no es una prueba válida de logout. No se renueva automáticamente un access
  token vencido para ejecutar el cierre remoto.
- Se actualiza solamente la fila correspondiente a esa sesión, sin revocación global.
- Repetir la petición con el mismo JWT aún vigente y la misma sesión ya REVOCADA devuelve
  204 sin reescribir revocada_utc. No concede acceso a otros recursos protegidos.
- Una petición demorada para la sesión anterior nunca selecciona una sesión nueva de la
  instalación. El login nuevo no espera una revocación pendiente.

| Respuesta | Significado |
|---|---|
| 204 sin contenido | Revocación confirmada tras commit, o confirmación idempotente autorizada |
| 401 SESION_INVALIDA | Prueba ausente/inválida/vencida, identidad inconsistente, cuenta no ACTIVA o sesión no autorizada |
| 503 AUTENTICACION_NO_DISPONIBLE | Configuración de credenciales o persistencia no disponible |
| 500 ERROR_INTERNO | Error inesperado sanitizado |

Los errores reutilizan `{codigo,mensaje,erroresPorCampo}` de RF02, sin tokens, hashes,
datos rechazados ni detalles SQL. Las respuestas llevan Cache-Control no-store.
No se crean cookies ni JSESSIONID. No se añaden secretos, dependencias ni duraciones.

La cadena HTTP permite que el POST llegue al caso de uso para verificar su prueba:
**no es una revocación anónima**. Sin JWT válido y pertenencia persistida no hay escritura.
El filtro normal de RF02 sigue rechazando sesiones REVOCADA; no se debilitó para permitir
la repetición idempotente de logout. Esta autorización restringida vive solo en RF06.

## Orden funcional y responsabilidades

El orden congelado se conserva como contrato de integración:

1. Android recibe la confirmación expresa del usuario.
2. Android prepara únicamente en memoria la petición autorizada con el access token actual.
3. Android elimina sus credenciales almacenadas y datos sensibles, conservando solo ajustes generales.
4. Android muestra Bienvenida sin esperar red.
5. Android intenta enviar la petición previamente preparada; descarta la información efímera
   al concluir el intento. No se aprueba almacenamiento de tokens tras la limpieza, cola ni reintento persistente.
6. Solo una respuesta válida confirma la revocación remota. Sin respuesta, el cierre local
   sigue siendo efectivo y no se afirma que el servidor haya revocado.

Los pasos Android se describen como obligaciones futuras: no hay código Android en esta entrega.
El backend no puede acreditar que se mostró un diálogo o Bienvenida, ni borrar datos del dispositivo.

## Persistencia y consistencia

Se reutilizan `AuthenticationStore` y `SessionCredentials` sin modificarlos. CloseSession
abre una transacción independiente y conserva el orden de RF02: usuario FOR NO KEY UPDATE,
luego sesión FOR UPDATE. Revalida expiración después de esperar los bloqueos.

El adaptador de escritura ejecuta UPDATE de mycar.sesion con filtro por id_sesion,
id_usuario, id_instalacion, estado_sesion VIGENTE y revocada_utc nula; fija estado_sesion
REVOCADA y revocada_utc con la hora del servidor PostgreSQL. Exige exactamente una fila.
La repetición ya revocada no ejecuta otro UPDATE. Se respeta ck_sesion_revocacion.

No se borran cuenta, preferencias, suscripción ni historial; no se modifican contadores de
login, refresh hashes u otras instalaciones. No existe tabla/cola de revocaciones pendientes.
La validación RF02 ya rechaza access y refresh de una sesión efectivamente revocada.
Login, renovación y cierre concurrentes usan el mismo orden de bloqueo; renovar no puede
reabrir una sesión que termine revocada. Ninguna operación pendiente selecciona la sesión
recién creada usando solamente el identificador de instalación.

## Límites y decisiones pendientes

- RF06 no está terminado de extremo a extremo: falta la integración Android completa y su prueba
  de almacenamiento sensible eliminado, petición efímera, navegación, cancelación y avisos.
- Si el access token vence, el backend devuelve 401 y no renueva ni confirma revocación. No se
  presenta ese resultado como fracaso del cierre local. Es la condición técnica aprobada.
- La desaparición de una respuesta nunca prueba que el servidor no haya hecho commit.
- No se introdujeron colas, persistencia de cierres pendientes ni reintentos automáticos.
- RF02 sigue pendiente en login de cuentas no ACTIVA e Inicio. Sus 47 pruebas no acreditan
  los comportamientos expresamente no implementados. RF01 conserva su pendiente legal de privacidad.
- Clave JWT y duraciones reales siguen siendo configuración externa de RF02, no fixtures de pruebas.
- No se modificaron Android, vehículos, documentos funcionales ni migraciones. Sin commits ni push.
